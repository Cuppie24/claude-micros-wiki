# ComponentOne (C1) package version bumps can exceed license coverage, breaking the build with an interactive popup

**Symptom** — A `msbuild ... /t:Build` run (no GUI involved anywhere else in the invocation) unexpectedly shows an interactive **"About Licenses — ComponentOne License Period Expired. Developer license required."** dialog on screen and hangs/fails. Console output (with `/clp:ErrorsOnly`) shows only:

```
Microsoft.Common.CurrentVersion.targets(3572,5): error MSB6006: "lc.exe" завершилась с кодом -1.
```

With more verbose logging, the immediately-preceding target is `CompileLicxFiles`, which shells out to `lc.exe` (`...\Windows Kits\...\NETFX 4.8 Tools\lc.exe`, the .NET Framework License Compiler) against every assembly referenced by `Properties\licenses.licx`.

**Root cause** — MESCIUS/ComponentOne licenses are perpetual-with-updates-until-a-cutoff-date, not tied to a specific version number. `lc.exe` validates every `C1.*` assembly listed in `licenses.licx` against the locally-activated license during `CompileLicxFiles`. If **any** referenced `C1.Win.*` package was bumped past a build released after the license's cutoff date, `lc.exe` can't validate it and surfaces this dialog — even though older C1 assemblies in the same project still validate fine. This is easy to misdiagnose as a generic "expired license" (implying nothing works) when it's actually **version-specific**: the fix is matching the referenced C1 package versions to what the local license actually covers, not renewing/activating anything.

A **partial** version bump makes this doubly confusing: in this case, `C1.Win.4.8`/`C1.Win.C1Command.4.8`/`C1.Win.C1FlexGrid.4.8`/`C1.Win.C1Schedule.4.8` had already been bumped (uncommitted, in-progress work) while `C1.Win.C1Input.4.8` was still on the old version — that mismatch caused an *earlier*, unrelated-looking crash first (`MissingMethodException` on `C1.Win.Localization.StringsManager.GetString` while loading a `.resx` during `GenerateResource`, `TypeInitializationException` on `C1.Win.C1Input.C1InputStrings..cctor()`). Bumping `C1.Win.C1Input.4.8` to match the others (the seemingly-correct fix for *that* crash) only moved the build one step further, into the license wall above — the version-skew crash and the license-coverage wall are two separate problems in the same partial upgrade, not the same problem twice.

**Fix**
1. Identify every `C1.Win.*`/`C1.*` `<Reference>` in the `.csproj` that's been bumped past the last known-good version (diff against `HEAD`/a known-working commit).
2. Revert `packages.config` + every affected `<Reference Include="..." Version="...">`/`<HintPath>` in the `.csproj` back to the old version, and remove any `<bindingRedirect>` in `App.config` that was added for it (if all references agree on one version again, no redirect is needed).
3. If NuGet already deleted the old package folder from `packages\` (normal behavior once nothing references it) and `nuget.exe` isn't installed on the machine (`msbuild /t:restore` is a **no-op** for classic `packages.config`-style projects — it only handles `PackageReference`/SDK-style restore, and silently reports "Работы нет" / "nothing to restore" instead of erroring, which looks like success but isn't), reconstruct the package folder by hand from the **locally-installed ComponentOne SDK** instead of downloading anything: `C:\Program Files (x86)\MESCIUS\ComponentOne\WinForms\bin\v4.8\*.dll` contains the exact assemblies the local license actually covers (verify with `[System.Reflection.AssemblyName]::GetAssemblyName($path)` — version *and* public key token should match the `.csproj` reference exactly). Copy the needed DLL into `packages\<PackageId>.<version>\lib\net48\<PackageId>.dll` — that's all a classic `<Reference HintPath>` needs; you don't need to fabricate the rest of a real `.nupkg` (`.signature.p7s`, `buildTransitive/*.targets`, docs, `tools/VisualStudioToolsManifest.xml`) for a project that doesn't consume those via `PackageReference` semantics anyway.

**Diagnostic-only workaround** (do **not** commit this, and don't treat it as a fix — it just lets you see *past* the license wall to check for other, unrelated compile errors without dealing with the license issue first): point MSBuild at a throwaway targets file that no-ops the target, via the standard SDK extension hook:

```xml
<!-- e.g. in a scratch file, NOT in the repo -->
<Project xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <Target Name="CompileLicxFiles" />
</Project>
```
```powershell
msbuild MyProj.csproj /t:Build "/p:CustomAfterMicrosoftCommonTargets=C:\path\to\scratch.targets"
```
`CompileLicxFiles`'s only condition is `'@(_LicxFile)'!=''` (see `Microsoft.Common.CurrentVersion.targets`) — no `GenerateLicenseFile`/`GenerateLicenses` property gates it in this MSBuild version despite that being a common assumption from newer SDK-style projects; passing `/p:GenerateLicenseFile=false` has **no effect** here. `CustomAfterMicrosoftCommonTargets` (imported at the very end of `Microsoft.Common.CurrentVersion.targets`, well after every target it defines, including this one) is the correct override point — the last definition of a target with a given name wins, and MSBuild lets you inject one externally via that property without touching the project or the shared SDK files at all.

**Checklist / rule**
- Before bumping any ComponentOne package, check whether *every* other `C1.*` reference in the project is already at (or being bumped to) the same/a compatible version — a partial bump produces a version-skew crash first, and completing the bump "correctly" (matching versions) can just reveal a second, unrelated license-coverage wall behind it. Don't stop at "the versions now match" — confirm the build actually succeeds.
- `msbuild /t:restore` silently succeeding with "nothing to restore" on a `packages.config` project is not evidence the packages were restored — it means that target doesn't apply to this project type at all. Check the `packages\` folder actually gained the expected version directory before trusting it.
- The interactive license dialog blocks whatever process popped it (don't assume a CLI build "hung" for no reason if a GUI window is involved) — if you trigger this via an automated/background build, warn whoever's at the keyboard before retrying, since the popup will resurface until the version mismatch is actually fixed.
- **This recurs, confirmed 4 times same day, from a genuine single-package update** — updating *only* `MC_GlobalForms` in Visual Studio's NuGet Package Manager (confirmed via screenshot of the single-package Update dialog, not "Update All" or a multi-selection - an earlier version of this entry wrongly blamed a batch-update UI action; that theory didn't survive the user directly refuting it) still re-bumps `C1.Win`/`C1.Win.C1Command`/`C1.Win.C1FlexGrid`/`C1.Win.C1Schedule` back to the unlicensed versions every time.
- **Actual root cause: the Package Manager's "Dependency behavior" setting is "Highest"**, and NuGet version syntax makes that dangerous. A bare version number in a `.nuspec` dependency (`<dependency id="C1.Win.C1Schedule" version="4.8.20231.596" />`, no brackets) is a *minimum*, not a pin - it means "this version or newer," equivalent to the range `[4.8.20231.596, )`. With Highest selected, the resolver doesn't stop at the stated minimum - for every such open-ended dependency, transitively, it walks to whatever's the newest matching build available in the configured source/cache. Confirmed concretely by extracting nuspecs from the `.nupkg`s (`[System.IO.Compression.ZipFile]::OpenRead(...)`, it's just a zip): `MC_GlobalForms` depends on `C1.Win.C1Schedule` (bare `4.8.20231.596`) → Highest resolves that to the newest cached build (`4.8.20251.721`) → *that* build's own nuspec depends on `C1.Win` (bare `8.0.20251.721`, package-version numbering, distinct from the `4.8.x` assembly-file-version scheme) → Highest resolves that to its newest too (`10.0.20261.813`, assembly `4.8.20261.813`). That's a real, confirmed two-hop cascade from updating one package. `C1.Win.C1Command`/`C1.Win.C1FlexGrid` are swept in the same pass (classic `packages.config` "Update" re-validates the whole project's package graph for consistency, not just the touched package's own subtree, once Highest is selected) - the exact intermediate link for those two wasn't traced further once the mechanism was already confirmed via C1.Win.C1Schedule/C1.Win, since chasing the remaining ~13 sibling C1.* dependencies MC_GlobalForms also declares for marginal extra certainty wasn't worth it.
- **Fix is identical every time**: re-diff every `C1.Win.*` reference in `.csproj`/`packages.config`/`App.config` against `HEAD` (or the last known-good state) and revert whichever drifted, reconstructing the old DLLs from the licensed SDK again if NuGet deleted those folders (it does, every time). Don't re-litigate the revert-vs-renew-license choice each time - once the user has chosen to revert, reapply that same choice directly on recurrence rather than asking again, unless something about the license situation has actually changed.
- **To actually stop the recurrence**: switch "Dependency behavior" from **Highest** to **Lowest** in the NuGet Package Manager before updating `MC_GlobalForms` (or any package with open-ended/bare-version dependencies) - Lowest resolves every such dependency to exactly what its nuspec declares, matching what the package author actually tested against, instead of opportunistically grabbing whatever's newest in the feed/cache.
- Deleting the newer C1 package folders from the local `packages\` cache (once reverted and no longer referenced by any `.csproj`/`packages.config` entry) is safe - it's gitignored, NuGet-restorable content, not source. Doesn't prevent Highest-mode resolution from re-fetching them from a remote source on a future update, but removes them as an already-cached "free" answer.

Found in: CWATIS, 2026-08-25 (four times, same day, same session) — first while completing an in-progress C1 package bump the user had left uncommitted; second through fourth immediately after, when updating `MC_GlobalForms` alone (1.1.6.24→1.1.6.25→1.1.6.26) silently re-bumped the same 4 C1 packages each time. Root cause was misdiagnosed as a batch/"Update All" UI action after the second occurrence (filesystem timestamps looked consistent with that theory), then corrected on the fourth once the user showed the actual single-package Update dialog - the true mechanism (Dependency behavior: Highest, bare-version nuspec deps treated as minimums) was confirmed by tracing the real transitive chain through extracted nuspecs.
